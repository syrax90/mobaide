# Documentation Registry

- README.md — Project overview: problem statement, client-agent-relay architecture, feature list (including device management), agent stack, and Google Sign-In configuration.
- docs/configuration-profiles.md — Configuration Profiles system: one PowerShell command swaps env-specific files (agent .env, android/local.properties, TLS trust config) between named profiles.
- docs/deployment.md — Central-server deployment to a VPS (deploy_central.py, cross-platform Python, LetsEncrypt or CloudflareOrigin TLS), the web-SPA deploy runbook (deploy_web.py: app.mobaide.com Caddy site block, atomic symlink releases under /opt/mobaide/www, CSP theme-boot hash procedure, gray-cloud DNS in both TLS modes), the *Capacity & revisit triggers* section (Tier-B load model, container caps, the 60 s `monitoring.sample` log line, Redis-split triggers), and per-machine mobaide_agent deployment on Windows (conda), Linux (systemd), and macOS (launchd), including crash-loop supervisor settings, the default-deny OpenAPI exposure policy (`ENABLE_API_DOCS`, admin-gated) for both the relay and the agent, the `FORWARDED_ALLOW_IPS` client-IP setting behind Caddy, and — under *Security response headers* — the universal `nosniff`/`Referrer-Policy`/`X-Frame-Options` set, the per-surface CSP table (site / portal / dashboard / API / Caddy-served SPA, plus the deliberate `/docs`+`/redoc` exemption and the one `style-src 'unsafe-inline'` concession Google Sign-In forces), the `CSP_REPORT_ONLY` soak runbook, the Caddy HSTS ratchet with its irreversibility caveat, why CORS is deliberately absent, and the WebSocket Origin allow-list (`WS_ALLOWED_ORIGINS`).
- docs/email-verification-workflow.md — Email OTP verification flow for email+password registration: happy/unhappy paths, SMTP setup (Mailpit dev, provider prod), rate-limiting knobs, security model.
- docs/password-reset-workflow.md — Password reset for email+password users via OTP-in-app: happy/unhappy paths, per-email + per-IP rate limits, mobile refresh-token revoke, password-changed notification, security model.
- docs/account-deletion-workflow.md — User self-service account deletion (CLA-61): Android Danger-zone flow and mobaide.com web portal share a 14-day soft-delete grace window backed by an audit-log table and a sweeper task; re-auth requirement, three cancellation paths (in-app, portal, email link), schema migration, config knobs, and the public `/portal/delete-account-info` URL submitted to Play Console.
- docs/terminal-view-fork-changes.md — Changelog of edits applied to the vendored Termux `terminal-view` and `terminal-emulator` Java sources (`TerminalView.java`, `TerminalViewClient.java`, `TerminalEmulator.java`, `TerminalSession.java`); single source of truth for fork drift on upstream rebase.
- docs/versioning-and-updates.md — Release tag conventions (android-v / agent-v / server-v / proto-v), signed-manifest format, staged-binary auto-updater state machine (build-without-pip venv → swap → final-path pip+wheel → `.installed` completion sentinel; "complete release" gating for rollback/prune/self-heal), install-script + trust-key bootstrap, Android version-gate / Play in-app update / agent-outdated-banner flows, release-please monorepo workflow with PAT caveat, server-side deploy gate, protocol-integrity CI gate (constants + golden + diff guard), end-to-end auto-update verification test.
- docs/release-publishing.md — Install-script publishing pipeline: deploy/install.* and deploy/windows_launcher.py on main → gh-pages branch root → get.mobaide.com. Includes the manual gh-pages sync runbook, what lives on gh-pages (install.sh, install.ps1, windows_launcher.py, CNAME, .nojekyll), and verification steps.
- docs/qr-pairing.md — Agent-initiated QR pairing flow (CLA-50): protocol & data flow, QR payload schema (`MOBA1|...`), relay_url persistence (pairing_tokens column, single source of truth for dispatch and WS-recovery paths), two-phase WS handshake (pending_pairing.json written after "ready" frame), TOFS trust-key pinning on the mobile, re-pair semantics (same-owner rotation; different-owner claim rejected with 409 — current owner must remove agent first), operator runbook (install-time, `show-qr`, `re-pair`, re-pair to different account, headless / SSH-disconnect behaviour), server-side config requirements (`MANIFEST_SIGNING_PRIVATE_KEY`), multi-worker caveat, troubleshooting (503 / 410 / fingerprint mismatch / Windows stdout-silenced v0.1.7–v0.1.8).
- deploy/prod/bootstrap-mobaide.md — One-time VPS bootstrap before deploy_central.py runs: server prerequisites, /opt/mobaide layout, .env seeding, ufw rules, TLS mode choice, optional SQLite backup cron.
- docs/ios-client.md — iOS client (SwiftUI, iOS 17+, `ios/`): project layout (hand-authored xcodeproj with synchronized folder groups), iPhone-only device support (`TARGETED_DEVICE_FAMILY = "1"`, Mac/Vision opt-out, and what widening it would oblige), the App Store privacy manifest (Required Reason API declarations, collected data types), the `ITSAppUsesNonExemptEncryption = false` export-compliance declaration and what would invalidate it, build/test commands, simulator setup and APNs sandbox testing (`xcrun simctl push` + real-device end-to-end steps), sign-in configuration (gitignored `Local.xcconfig` overrides, Google client ids, server-side `APPLE_CLIENT_ID` for `POST /api/auth/apple`, the shared nonce scheme), the notifications pipeline (iOS-09 local attention alerts + iOS-10 APNs push registration/delivery), the Android→Swift protocol-parity approach (wire-key-verbatim Codable, kotlinx default/coercion parity, WebSocket backoff/close-code semantics, relay routing), known deliberate byte-level deviations, and the `tests/protocol_fixtures/` golden-fixture format with its bidirectional registry check.
- PROTOCOL.md — Wire-contract reference: the single integer protocol_version that gates Android / mobaide_agent / central_server compatibility, application-level WebSocket close codes (4001 auth-failed, 4002 protocol-incompatible with manifest_url hint, 4010 admin-revoked, 4011 admin-force-disconnect, 4012 agent-transient-offline), HTTPS-bootstrap auto-update path (three firing triggers: startup pre-flight, 4002 recovery, 60-min poll), and how to bump the version (including the HTTPS-bootstrap pre-requisite checklist item).
